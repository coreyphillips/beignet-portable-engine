What 0.23.0 changes for this fork. Fees (#998, #1001, #1008, #1017): every Lightning pay path now sends under a fee cap. A caller that passes neither `maxFeeSats` nor `maxFeeMsat` gets 1% of the amount rounded up to the msat and never below 50 sats (`defaultMaxFeeMsat` in `BeignetNode`; the engine itself keeps `undefined` as uncapped), an explicit cap still wins, and both at once is refused `INVALID_PARAMS` before anything is reserved. The shared client always sends `maxFeeSats`, the `estimatedFeeSats` of `POST /payment/estimate` plus its headroom, and that estimate now rounds up where it floored before (a cap set at the quote could refuse the very route it priced), so the default reaches only a caller of the portable router that omits both; the router now also forwards `maxFeeMsat`, the exact cap, and the estimate carries `estimatedFeeMsat`. A route over the cap is refused `FEE_EXCEEDS_MAX`, now a permanent refusal rather than a retryable `PAYMENT_FAILED`; `payInvoiceSafe` never throws, so the router's caller sees it as a FAILED record whose `failureDescription` carries the code. The fee a payee wrote into a BOLT 11 blinded path was outside every cap and under-reported on the record; it is capped and reported now, and the path's htlc bounds are enforced. `maxPaymentSats` and the daily limit judge the amount plus the cap at admission and charge the amount plus the fee actually paid; the runtime spreads its `nodeOptions` into `BeignetNode.create`, so a host that sets either limit sees the new refusal wording, and a host that sets none is unaffected. An MPP record carries `sentMsat`, what left the node fees included. Channels (#1009, #1020): an inbound HTLC whose expiry is at or below our own tip is admitted and failed back once committed (stamped `expiredOnArrival`) instead of failing the channel, so the home channel no longer force-closes over a stale add, and the node never offers an HTLC whose expiry is at or below its tip; as a forwarder the engine applies `expiry_too_soon`, which the phone, forwarding nothing, never exercises. On a channel the phone funds (a channelize open, or a channel its own deposit opened), an inbound add the funder could no longer pay the commitment fee for is admitted and failed back inside the band that the sender's own view of our commitment affords, and refused on the wire only where our output would be trimmed; `hasBeenSpliced` is set when a splice completes and, on such a channel with fewer than five HTLCs in flight, the guard uses eclair's climb-out rule (a balance above the fee admits, reserve or not), which is the home channel's shape once it has been grown by a splice. A channel row written before this baseline lacks the flag and reads as never spliced until its next completed splice. On-chain (#1002, #1011): the wallet's staged send is reset after every `sendMany`, `sendMax`, `buildPsbt` and sweep, a stored staged send with inputs or outputs left by an older version is replaced at boot (a clean one costs no write), and an external signing key is never written to wallet storage; the portable router exposes none of these routes, its only on-chain send being direct funding, so the phone meets this as the boot check alone. Files (#1004): `BeignetNode.create` calls `ensurePrivateDir(dataDir)`, `SqliteStorage` tightens the database file and its sidecars on construction and after `open()` and each `backup()` destination, and the SCB export and the capsule-restore marker go through `writeFileAtomic`. In the bundle `process.platform` is `browser`, so the helpers run and land on `portable/fs.ts`, where `mkdirSync` and `chmodSync` are no-ops, `statSync` reports no `mode` (nothing is tightened) and throws `ENOENT` for a directory (caught by `tightenMode`, so `create` logs no warning), and `writeFileAtomic` ends in the volume's `rename`, the path the capsule marker already took; nothing on the phone changes. The `process.umask(0o077)` call is in the CLI only. Daemon and CLI only, none of it in the bundle: the browser guards and the token `beignet init` mints (#1005), the request target parsed against a constant base and the process fault handlers (#1003), and the three new refusal codes those add to `BeignetErrorCode`.

## Upstream surface this fork does not expose

Beignet 0.15.0 added `src/lightning/swaps/` and a reverse swap provider (Lightning to on-chain); 0.16.0 added the submarine direction (on-chain to Lightning) in `src/lightning/swaps/submarine-engine.ts`. `src/lightning/node/lightning-node.ts` imports both statically, so the modules are present in the bundle, but every swap path is gated behind `config.swaps.enabled`, which the portable runtime never sets, so neither provider is ever constructed. The portable router deliberately does not expose the daemon's `GET /swaps/status`, `GET /swaps` or `POST /swaps/cancel`. Serving swaps in either direction is a provider role that locks the node's own coins in contracts for peers; both are off by default upstream and neither is a wallet feature. The engine still ships no wallet-side swap client; 0.16.0 places that in a separate client package.

The same release added a second JIT opening-fee collection mode. `POST /jit/invoice` now accepts and returns `feeMode`: `skim` deducts the fee from the delivery, `hop` bills the sender through the invoice routing hint. The shared client names `skim` on the wire and refuses any other mode, because the receive quote it showed the user priced a deduction.

0.17.0 adds an optional `cltvLimit` to the four pay routes, bounding a payment's total CLTV expiry against the current tip (a `CLTV_EXCEEDS_MAX` refusal, or `CHAIN_NOT_SYNCED` when there is no tip). It exists so a swap provider can bound a payment against its refund height; it is not a wallet need, so the portable `POST /invoice/pay-safe` does not forward it and the shared client does not send it. The release's other change, the durable zero-conf splice rebroadcast obligation, is the reason it was taken and is described in the README.

0.21.2 adds `POST /direct-funding/prepare`, which reads a request and starts dialing the node a send of it would talk to first, so a dial over Tor is not queued in front of the exchange once the user presses Send. It spends and records nothing. The portable router does not expose it: it is a payer-side latency optimisation, and the phone is the receiver in the flow this fork drives. The same release adds an optional `chainWaitMs` to the receiver policy; the portable runtime leaves it at the engine default of 20 seconds.

0.18.0 and 0.19.0 are splice-safety releases: a confirm-first splice for a stranger's direct funding with a conflict revert, and four fixes around splices that are confirmed but below their lock depth, splicing channels and HTLC backstops, retracted splice sightings, and funding spends mined below `minimumDepth`. The direct-funding receiver policy gained `allowUnpairedSplice` (default off) and `unpairedSpliceDepth`. `portable/lfbw.cjs` now sets `allowUnpairedSplice` next to `allowSplice`, matching the host manager's rules, and leaves the depth at the engine default of three confirmations, so an anonymous Beignet payer's confirmed coin grows the home channel rather than opening a second one; an anonymous payer whose coin is unconfirmed still gets a new confirmed channel, and a second such offer while one splice is confirming is declined so the payer falls back to a plain send that channelizes on its own. `portable/runtime.ts` listens to the four splice events and the accepted-offer event only to keep two fields on the wallet record for the client's notes. Enabling the live check for this exposed that the portable bundle had never minted a direct-funding envelope at all: `buffer@6` has no `base64url` encoding, the envelope encoder uses it, and the shared client turns a failed mint into a warning and a plain request. `portable/globals.ts` now maps `base64url` onto base64 for `toString`, `from`, `write`, `byteLength` and `isEncoding`, matching Node byte for byte (`portable-tests/buffer.test.cjs`). The four new splice events are not exposed by the portable router, which has no event stream; the wallet learns a splice's outcome from `GET /channels`, its own submission journal, and the two record fields above.
