# Portable engine validation, 2026-09-09

The fork now tracks upstream Beignet **0.19.0** (`f352119`, tag `v0.19.0`); it was resynced from 0.17.0 on 2026-09-10, from 0.16.0 and 0.15.0 on 2026-09-09, and from 0.14.0 on 2026-09-07. Each patched tree was verified to differ from its pristine tag by exactly the fork's own patch set. For 0.19.0 that check compared the reapplied tree's diff against pristine `v0.19.0` with the fork's own diff against pristine `v0.17.0`: the same 16 patched files plus the fork-only batch module, 44 hunks, and line-for-line identical added and removed content, with every hunk applying without rejection or fuzz, which is what shows that no fork hunk overlapped an upstream one and that reapplication reverted nothing upstream, even though upstream rewrote much of the chain watcher around the fork's one timer hunk there. 0.18.0 and 0.19.0 were taken for their splice-safety fixes; they add no dependency, route, config flag or storage migration. 0.17.0 was taken for its durable zero-conf splice rebroadcast obligation (upstream #756), the defect this fork had previously recorded as belonging upstream; its other change, `cltvLimit` on the pay routes, is a swap-provider need the wallet does not use. 0.16.0 was taken for four payment-integrity fixes in `lightning-node.ts` (MPP records journaled before their HTLCs, a preimage still reported when the outgoing record is gone, a keysend on a hash this node is paying refused, and no pruning of records with live HTLCs), not for its submarine swap provider, which, like the reverse provider, stays gated behind a flag this runtime never sets. 0.16.0 adds no runtime dependency. The current build and all **42 portable tests** pass. They cover the direct-funding policy (a stranger's confirmed coin may splice the home channel, the depth left to the engine) and the `base64url` encoding the direct-funding envelope needs, byte for byte against Node; AES-256-GCM and ChaCha20-Poly1305 interoperability with Node and authentication failures; onion ChaCha20/HKDF/hash/HMAC parity; Hermes-style Buffer subarrays retaining zero-copy views and integer readers; SQLite transactions, rollback, durable failure poisoning and BLOB compatibility; runtime ownership, corrupt-registry handling and explicit offline backup access; every supported network's genesis and mismatches, including the actual runtime before database/peer access; exact splice transaction binding; and bounded gossip persistence batching.

Connection diagnostics additionally cover a real authenticated relay upgrade followed by TCP refusal reaching the compiled portable socket as an actionable error before its close event. Fixed refusal/DNS/timeout/TLS/unreachable categories, arbitrary payload redaction, endpoint sanitization, and explicit shutdown without duplicate errors are tested. The sibling relay's 16 tests and host's 39 tests also pass. The test runner needs permission to bind ephemeral loopback sockets; the initial restricted run failed with `EPERM`, and the network-enabled reruns passed.

`node scripts/regtest.cjs` completed with exit code 0 against the existing local Docker regtest chain, rerun on the 0.19.0 engine with the upstream checkout built at `v0.19.0` as the disposable primary, as did `node scripts/smoke-regtest.cjs` against the local CLN fixture. Its output was:

The last three, added on 10 September, drive a second upstream node with no pairing to pay the wallet's unified request by direct funding and check that the wallet still has exactly one channel with its primary, larger than before, once the splice locks at depth. Adding them exposed that the portable bundle had never minted a direct-funding envelope (no `base64url` in the bundled Buffer polyfill); the globals now supply it.

This uses the real bundled portable engine, shared `EmbeddedWalletClient`, SQL.js durable snapshots and the sibling byte relay. A disposable original Beignet primary receives 5,000,000 regtest satoshis, opens the channel, pays a 12,000-satoshi portable invoice, receives a 3,000-satoshi payment, and participates in a 2,000-satoshi external splice. The test verifies the splice's actual transaction before restarting the engine, then confirms its exact output and original funding input on-chain. After restart, channel reestablishment and prior settled payment history are checked. Wallets, relay and primary are shut down and the temporary directory is removed in `finally`. No funded integration processes remain running.

The initial experiment that closed the wallet immediately after asynchronous splice acceptance did **not** establish a completed external payment; its durable submission remained pending. The passing restart test waits for verified broadcast first. Acceptance alone is deliberately never reported as completed. Keep a wallet open while a pending operation negotiates; an interrupted operation with no conclusive chain evidence remains pending/uncertain until resolved.
